# v0.3 Bidirectional Mixin Navigation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete generic, tested Config-to-Mixin and Mixin-to-Config navigation using one bidirectional graph.

**Architecture:** Providers receive search evidence and emit shared links containing every controlling field. Service coordinates searches and deduplication. Cached gutter data stores smart pointers and uses PSI modification invalidation.

**Tech Stack:** Kotlin, IntelliJ Java PSI fixtures, ReferencesSearch, PsiSearchHelper, SmartPsiElementPointer.

**Spec:** `docs/superpowers/specs/2026-09-23-gtnh-development-v1-design.md`

## Global Constraints

- Preserve v0.2 forward navigation.
- No production Hodgepodge identifiers or method-name allowlists.
- Search project scope off EDT and respect cancellation/dumb mode.
- Gutter collection must never start project-wide discovery.

## Review Focus

- Two Mixins with the same simple name return both candidates instead of guessing.
- `Config.foo && !Config.bar` returns both fields.
- Ordinary references to config fields and Mixins produce no false link.
- Broken class/string references return empty or partial results without exceptions.
- Editing registration source invalidates cached gutter relationships.
